## Required capability and caller integration

For behavior that depends on information or control outside the proposed component,
trace the real production path before calling the plan executable. Name who supplies
the input, when it exists, how each caller or wrapper transports it, and which owner
keeps it valid and releases it. A new interface, requester, identifier or scope does
not create information that no producer captures. Check every applicable renderer,
direct public call, compatibility wrapper, nested owner and call without optional
setup. Inspect only the paths needed to answer these questions.

Read configured project rules before fixing proposed public types, parameter names
and integration requirements in a spec. Reconcile new signatures with mandatory lint
and supported platform APIs through source inspection. Choose compliant details when
the operator has left them open. An exact operator requirement that conflicts with
those rules needs an explicit decision; suppressions or invented capabilities do not
resolve it. Build and validation execution remain with their owning phases.

Before assigning criteria to subtasks, check shared prerequisites across all affected
criteria and consumers. Plan acquisition, transport, fallback and lifecycle ownership
before the behaviors that depend on them. Preserving a function signature does not
prove that existing calls supply a newly required input. If caller registration or
setup must change, name those edits and reconcile them with compatibility and scope
constraints. A helper installed by an optional theme or host cannot cover valid calls
that omit it. Missing local wiring can be planned when authorized; do not classify it
as an unavailable external capability merely because it has not been implemented.

Before requesting a contract amendment during repair, trace that same prerequisite
through the affected criteria and consumers in the supplied governing spec. Report
its complete known impact and a concrete supported alternative in one decision request,
including acquisition, transport and compatibility changes. Distinguish signatures
from caller obligations. Do not propose a component-only exception that leaves the
same known conflict in a sibling consumer. This inspection does not reopen accepted
criteria, expand the runtime-selected repair, or authorize edits to another spec.
If sibling governing context is unavailable, name that limit instead of claiming
complete impact coverage.

Apply existing operator decisions to their actual scope. A retry or permission to
inspect is not authority to change a contract. A decision for one component does not
authorize sibling integration unless it says so. When a decision is still required,
report the remaining conflict and the smallest complete amendment supported by the
evidence. Preserve the original requirement and completed work. Never call a partial
or unsupported plan ready, and do not repeat a resolved conflict as a new blocker.
