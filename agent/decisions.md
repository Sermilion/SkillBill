## [2026-10-17] Discovery names the open criteria in prose and each gap is verified once
Context: After discovery found any gap, every criterion still got a focused audit, including ones discovery had found met, and each repaired criterion got a second read-only audit after its targeted verification. A subtask with eight criteria spent about fourteen audits where four were needed.
Decision: The initial full audit ends its prose with one line, `Open criteria: AC-002, AC-005` or `Open criteria: none`. The runtime reads that line leniently: criteria it does not name are accepted at once, named criteria queue in spec order and go straight to plan fix, implement fix and one targeted verification audit, with up to three unsuccessful cycles each. When the queue empties the run moves on. If the line is missing or names no queued criterion, the runtime falls back to auditing every criterion; it never blocks on the line.
Reason: Discovery already established which criteria have gaps; auditing met criteria again and re-auditing a verified repair duplicates work. A prose line keeps the workflow prose-based and adds no structured settlement field or new block reason.
Alternatives considered: A structured `open_criteria` settlement argument was rejected because it adds block reasons to a prose workflow. Parsing free prose without a marker line was rejected as too fragile.
Revisit when: Discovery agents routinely omit or misreport the Open criteria line.

## [2026-10-17] Acceptance repair trusts per-criterion results and has no final full audit
Context: SKILL-426 added a final full source audit after the per-criterion repair queue emptied. That audit re-checked every criterion at once and, on any gap, re-queued criteria that focused audits had already accepted, so a run could keep cycling through whole-spec audits after every criterion was settled.
Decision: The loop keeps one initial full discovery audit, then settles one criterion at a time with up to three unsuccessful repair cycles each. When the queue empties the state becomes `ACCEPTED` and the run moves to review. There is no final full audit and no re-check of accepted criteria. The final-audit stage, fields, payload keys and schema entries are removed outright with no legacy read path. This supersedes SKILL-426 AC-005.
Reason: A focused audit that accepted a criterion is the authority for it; re-auditing everything at the end duplicates work and lets one regression report reopen the whole queue.
Alternatives considered: Keeping the final audit but scoping its reopen to named criteria was rejected because it still checks every criterion at once. Keeping the removed stage readable for old rows was rejected; there is no backwards compatibility requirement.
Revisit when: A later repair is shown to break an earlier accepted criterion in a way review and validation do not catch.

## [2026-10-16] Acceptance criteria never include tests
Context: Plan-authored specs turned test expectations into acceptance criteria (for example "T3/T6 tests exist"). Audit already excludes test-only criteria, so such criteria could never be accepted by audit, stayed open until validate, and kept implementation and audit loops chasing work that belongs to later phases.
Decision: Acceptance criteria describe production end states only. The plan spec contract (`feature-spec-directive.md`), the plan feasibility constraint and the preplan intake forbid test-only criteria and criteria that name a test, test class, fixture, coverage, regression case or a guard's synthetic-violation case. Required tests go under a `## Test Obligations` section, and validate runs them.
Reason: Every criterion must be checkable by audit against production source; tests are evidence produced and run by later phases, not end states of the change.
Alternatives considered: Keeping test criteria and teaching audit to defer them was rejected because it already does, and the criteria still blocked acceptance and confused repair loops.
Revisit when: A change's deliverable is itself test infrastructure, such as a new architecture guard, and needs criteria of its own.

## [2026-07-15] Full local installs are the default for maintainer work
Context: Non-interactive `./install.sh --from-source` falls back to detected agents, base-only platform packs, and anonymous telemetry, which can leave follow-up validation without routed platform-pack coverage or full diagnostic telemetry.
Decision: Maintainer install refreshes in this repo should use the full install shape: detected agents, every platform pack (`platform-mode=all`), MCP registration, and full telemetry unless the user explicitly asks for a narrower install.
Reason: Skill Bill features often touch routing, staging, telemetry, platform-pack sidecars, and generated installed output; base-only or anonymous installs can make validation evidence incomplete or cause later workflow confusion.
Alternatives considered: Relying on the installer prompt defaults of base-only/anonymous was rejected because this workspace uses install refreshes as validation evidence, not just minimal local setup.

## [2026-05-02] orchestrator-owned-skill-override-enforcement
Context: `.agents/skill-overrides.md` carries per-skill mandates targeting orchestrator lifecycle (e.g. `mcp__personal-graph__session_start` before applying skill body, `write_state`/`write_episode` at end). The shared `orchestration/shell-content-contract/shell-ceremony.md` already had a `## Project Overrides` section telling skills to read the override file, but the rule was underspecified: it did not say the read is orchestrator-owned, did not require executing action mandates contained within, and did not name the lifecycle positions where mandates fire. A feature orchestrator that delegated the read to a subagent saw the action mandates paraphrased into a free-form `standards_notes` string and dropped in practice. Across four 2026-05-02 runs (SKILL-33 FU2/FU3/FU4 + SKILL-34) the personal-graph mandate was silently skipped on every run.
Decision: Override-section enforcement is fixed at the ceremony layer, not per-orchestrator. The `## Project Overrides` section in `orchestration/shell-content-contract/shell-ceremony.md` (consumed by 27 governed skills via sibling symlinks) now explicitly states that the read is orchestrator-owned and not delegable, names the two lifecycle positions where action mandates fire (preflight before skill body / postflight at end of skill before terminal `*_finished` telemetry), specifies the substring-match heuristic for detecting mandates (`mcp__*` tool calls, `read \`{path}\`` files, `write_state`/`write_episode` writes), and prescribes a structured result-recording shape. The pre-planning subagent's job is to surface override mandates (verbatim + structured `override_action_mandates` field in its RESULT JSON), never to execute them. This decision is repo-wide.
Reason: Subagent abstraction loss. Mandates aimed at the orchestrator's own lifecycle position cannot be fulfilled by a subagent that runs at a different lifecycle position. Fixing it once in the shared ceremony eliminates the abstraction layer where mandates get paraphrased away and propagates to every skill that links the canonical file — repo-wide enforcement at one edit cost.
Alternatives considered: (1) Add Step 0 / Step 9b prose to each orchestrator's `content.md` — rejected because `content.md` is the user-editable execution body, not the orchestration scaffold; the rule belongs at the ceremony layer where it can apply to every skill uniformly. (2) Tighten only the pre-planning briefing — rejected because it leaves the orchestrator-ownership question unsolved; mandates targeting before-skill-body and end-of-skill cannot be executed by a mid-flow pre-planner. (3) Add a runtime-level enforcement check that fails skills that skipped preflight — rejected as out of scope for SKILL-35; the static-string test asserts the prose says the right thing, which is sufficient for documented protocol. (4) Build a generic skill-override interpreter — rejected as premature; the substring-match heuristic is good enough until a mandate shape escapes it.
Revisit when: A new mandate shape escapes the substring-match heuristic (e.g. a mandate that doesn't name an `mcp__*` tool, a file path, or a write call). Or when ceremony enforcement needs to be machine-asserted at runtime rather than via static-string tests.

## [2026-04-21] top-level-orchestrators-use-workflow-contract
Context: Skill Bill already has multi-step feature orchestrators, but their step graph, retry rules, and artifact handoff mostly lived in skill prose and telemetry conventions.
Decision: Add a governed workflow contract under `orchestration/workflow-contract/PLAYBOOK.md` for top-level orchestrators only, starting with the feature workflow.
Reason: Durable workflow state belongs above reusable skills. This keeps stack routing and rubrics in standalone skills while giving long-running parent flows one authoritative place for step ids, artifacts, resume semantics, and parent-owned telemetry.
Alternatives considered: Turning every skill into a workflow was rejected because it would duplicate leaf-skill contracts and blur the stable user-facing command surface.
Revisit when: Skill Bill is ready to persist workflow state in runtime code or when a second top-level orchestrator adopts the contract.
