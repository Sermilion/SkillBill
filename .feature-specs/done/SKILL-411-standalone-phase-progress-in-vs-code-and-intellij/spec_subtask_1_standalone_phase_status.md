## Scope

## Acceptance Criteria

1. AC-001: The canonical IDE-status schema, Kotlin contract pin, serializers, parity fixtures, and both plugin decoders define the same versioned execution-scope, invocation identity, authoritative run-order, snapshot revision, and optional bounded current-activity contract. Scope-specific invariants distinguish workflows from standalone phases even when a durable standalone plan has a workflow id; unsupported versions and malformed payloads have explicit typed diagnostic mappings.
2. AC-002: A purpose-built SQLite standalone-phase status repository, additive migration, and established persistence ports retain canonical repository/branch correlation, invocation identity, lifecycle, timing, lease, and terminal result independently of WorkItem and telemetry rows. Transaction and reconciliation code prevents premature success, terminal regression, and classification of lost execution as done.
3. AC-003: Launch and lifecycle publication code covers durable standalone plan and in-memory review, validation, PR, and monitor without changing their operation semantics. Projections retain requested phase identity, current internal step, timing/liveness anchors, and only available activity. Terminal publication follows the complete authoritative operation result; review findings and a monitor result of nothing to monitor remain representable completed results.
4. AC-004: Workflow and standalone candidates share a persisted per-repository execution sequence and pass established eligibility/correlation gates before ordering. Selection code chooses a newer completed phase over an older active workflow and a newer workflow over an older phase regardless of timestamp ties, projects a durable plan once, preserves the latest eligible terminal result during retention, and maps expired execution leases to interrupted/stale state.
5. AC-005: VS Code domain, persisted cache, refresh, UI mapping, status bar, tooltip, details, and accessibility carry and visibly distinguish standalone phase scope, phase/status, available activity, and normal timing. Terminal timing freezes; failed, blocked, interrupted, and stale outcomes have non-success presentation; status-bar output remains bounded to 48 characters.
6. AC-006: IntelliJ domain, persisted cache, coordinator, UI state, native widget, popup details, and accessibility implement the same scope, latest-run, activity, lifecycle, and timing distinctions while retaining EDT/process isolation, coroutine cancellation, and established active-duration calculations.
7. AC-007: Both plugin coordinators and persisted caches preserve run identity, order, and revision across initial load, polling, reconnect, and fallback. Their acceptance logic rejects older runs/revisions and terminal regression, marks cache/transport fallback stale, handles store-generation replacement and correlation changes explicitly, and permits recovery of retained terminal timing without inventing optional activity or progress.
8. AC-008: Focused deterministic regression tests and governed parity fixtures cover wire compatibility and precision, migration/persistence/interruption, cross-source ordering, phase lifecycle publication, and each plugin's initial-load/reconnect/presentation boundaries. Every added test has a named realistic wrong behavior and observable outcome, and existing parity and real regression coverage remains intact.

## Implementation Details

### 1. Define the coordinated status contract and typed ownership (AC-001)

Start with `../../../orchestration/contracts/ide-status-schema.yaml`, `IdeStatusContractVersions.kt` under runtime-contracts workflow/identity/status, the port `IdeStatusModels.kt`, engine work/model `IdeStatusModels.kt`, and `IdeStatusSchemaValidator.kt` in runtime-infra/contracts. Target 0.3 and update VS Code and IntelliJ `domain/Constants` plus parity fixtures in the same change. Confirm the digest's 0.2 current pin only during implement; accommodate an intervening version without lowering a pin.

For execution-bearing snapshots, require explicit `execution_scope` (`workflow` or `standalone_phase`), `execution_id`, stable database-generation `status_store_id`, and canonical positive decimal-string `run_sequence` and `status_revision`. The first allocated sequence/revision is 1. Strings remain strings in serialization and both plugin domains/caches, including values greater than 2^53; comparisons use arbitrary-precision integer or normalized decimal-string ordering, never JavaScript Number. A sequence identifies one root execution in a canonical repository within a store generation. An execution id remains stable throughout that run; standalone `invocation_id` identifies that invocation and changes on explicit root resume.

Standalone scope additionally requires `phase_id` and `invocation_id`; an associated durable `workflow_id` is allowed and never changes scope. Workflow scope forbids standalone identity. Idle/problem-only snapshots do not invent execution metadata; when a diagnostic accompanies a retained execution it preserves that execution's identity. Keep the existing internal `currentPhaseExecution` distinction and liveness-only `last_agent_activity_*` semantics. Preserve strict unknown-property handling and enforce scope combinations in schema and typed constructor/init invariants. Extend `ideStatusSchemaWireMap` using owning key constants, enum wireValue tokens, and existing validator/typed runtime failure patterns. Unsupported version, missing/malformed identity/order, and conflicting scope have explicit schema-incompatible/degraded diagnostics rather than coercion.

Decision for the unspecified activity shape: `current_activity` is optional bounded text produced from allowlisted event descriptors, omitted when unavailable. Cap at 160 Unicode code points after redaction and control-character removal; truncate safely at code-point boundaries. Never publish raw agent text, commands, paths, tool output, credentials, or unrestricted diagnostics. Decoders enforce the same wire bounds; details may show the full bounded value and bars may shorten it. Do not repurpose activity as percent progress or heartbeat evidence.

### 2. Own persisted execution identity, standalone status, and fenced updates (AC-002, AC-004)

Add a typed `StandalonePhaseStatusRepository` and model under `runtime-ports/.../ports/idestatus/`, its SQLite implementation under `runtime-infra/sqlite/.../sqlite/idestatus/`, a purpose-built UnitOfWork property, and composition in `SQLiteUnitOfWork` in `SQLiteRepositories.kt`. Register an additive area migration in `DatabaseMigrationEntries.kt` and `core/migration/area/`. Use the next available identifier, expected 50; implement confirms the slot and existing port naming conventions. Keep SQL, connections, transactions, and resource lifetime inside SQLite.

Create a stable store-generation identity plus an execution registry/high-water counter per canonical repository, independent of status-row retention. Workflow and standalone launch registration use this common registry transactionally. Standalone rows retain canonical repository identity and captured branch correlation, requested phase/invocation, optional durable workflow correlation, execution id/sequence/revision, lifecycle/result, current step/activity, start/update/finish timestamps, active-duration accumulator/anchor, and lease owner/generation/expiry. Add correlation/eligibility indexes. Backfill existing workflow executions deterministically by authoritative start time with stable identity as the tie-breaker; backfill and pre-migration polling are not new launches. Counters never decrease when records are cleaned up.

Use narrow operations for idempotent launch registration/sequence allocation, eligible reads, lease-and-revision-fenced updates/transitions, and interruption/retention reconciliation. Two independent launch transactions cannot share a sequence. Repeating registration of the same execution returns the same registration. Heartbeats, polls, nested steps, and phase changes do not allocate sequences. Explicit root resume creates a fresh execution/invocation identity and sequence, keeps workflow correlation and accumulated timing, and cannot let events from the old generation update the new execution.

One owner controls coupled state transitions. Every update atomically checks lease generation/ownership and expected revision and advances revision only for an accepted persisted change. Terminal rows cannot regress or resurrect, including from late events or stale leases. Duplicate terminal notifications are idempotent. Durable plan records terminal success in the authoritative settlement transaction when possible; otherwise reconciliation reads authoritative settled plan state before publishing terminal success. No projected status leads authoritative settlement.

Reuse existing lease/liveness cadence and duration policy; implement locates its concrete owner rather than inventing intervals. Lease expiry exposes paused/stale with `runner_interrupted`, never done. Authoritative failure may reconcile interruption to failed; a late completion without authority cannot turn lost execution into success. Retain terminal result and frozen timing across restart for the existing six-hour settled window, protect the selected eligible terminal record inside that window, and reuse the existing 24-hour live/blocked retention owner. Storage/read/reconciliation faults emit typed RuntimeDiagnostics, preserve the underlying phase result, and never re-execute an irreversible phase operation.

### 3. Publish root phase lifecycle and select the authoritative latest run (AC-003, AC-004)

Wire the narrow publisher through `PhaseRunRequest.eventSink`, `FeatureTaskRuntimeRunEventSink`, `PhaseRunEntry.run`, `InMemoryPhaseRunState`, `StandalonePlanLauncher`, and `StandalonePlanRun`, with construction only in the composition root. Locate the canonical workflow root launch/resume owner during implement and register the common sequence there. Missing exact symbols in the digest are an implementation lookup, not permission to allocate on reads.

Capture requested standalone phase once for plan/review/validation/PR/monitor. Internal commit_push, monitor, fix-loop, gate, and review steps may change without changing requested phase. Map only observed PhaseStarted, PhaseLoopEdge, PhaseFixLoopIteration, ValidationGateProgress, PhaseCompleted, PhaseBlocked, and PhasePaused events to available current step/activity and persisted anchors. Liveness and activity remain distinct.

For in-memory invocations, `PhaseRunEntry.resultOf` and the complete PhaseRunResult/authoritative exception settle the invocation. An intermediate PhaseCompleted event, process exit, or unconditional finally cannot publish success. Preserve whole-run Completed/Blocked/Paused/Decomposed meanings. Completed review may contain findings; completed monitor may say no open PR/nothing to monitor. Cancellation propagates, persists non-success evidence where feasible, and leaves interrupted/stale evidence if final publication is lost. Durable plan stays durable and correlates its invocation with its workflow without changing operation return behavior.

Extend IdeStatusService, IdeStatusCandidate, IdeStatusProjector, IdeStatusSelectionPolicy, IdeStatusLivenessAnchors, and IdeStatusRepositoryCorrelation. Merge standalone candidates only after established repository/branch/issue/goal-authoritative eligibility. Deduplicate an associated durable plan workflow into its standalone invocation candidate. Across eligible distinct root executions, the common persisted sequence precedes lifecycle tier, freshness preference, timestamps, and response arrival; use established retention and correlation before this ranking. Equal sequence with conflicting execution identity is a typed invariant failure. Within one execution, authoritative persisted revision and lifecycle govern the projection. A newer completed phase beats an older active workflow; a newer workflow beats an older phase even under equal/skewed timestamps. Preserve WorkItem authoritativeUpdatedAt for workflow liveness and provide the equivalent standalone persisted lease/update anchors.

### 4. Apply the same acceptance protocol in each native consumer (AC-007)

Carry scope, identity/store/order/revision, phase/current step, optional activity, and terminal timing through SkillBillStatusOutcome, LastKnownDisplayCache, JSON mapping, and StatusRefreshCoordinator in each plugin. Keep the CLI command and serialized refresh. Cache data is stale until corroborated by a successful current response. Within one repository/correlation and store, higher sequence wins; equal sequence requires matching execution id and nondecreasing revision; same-run terminal state cannot regress. Compare decimal strings exactly, including very large values.

A different store id is a database-generation replacement accepted only from the latest successful serialized refresh generation. It invalidates old-domain ordering/cache and discards late responses from the previous generation. Existing repository/project/branch changes invalidate correlation independently of sequence. Disposal, reconnect, switching repository, and generation replacement cancel or discard in-flight requests under existing process isolation. Preserve the existing one-sample uncorroborated-idle tolerance and retention-expiry plus fresh-success corroboration. Idle invents no sequence; failures, timeout, malformed/version-mismatched responses, and reconnect transport errors are never authoritative idle.

Extend existing cache owners and sanitizers rather than creating new infrastructure. Legacy cache entries without ordering metadata may display as stale but must yield to the first valid current snapshot. Invalid ordering/scope or unsupported data cannot become fresh done. A newly opened plugin obtains retained terminal outcome and frozen timing from runtime status even with no cache. Missing activity/progress produces no placeholder progress.
