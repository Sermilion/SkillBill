## Acceptance Criteria

1. Internal STANDALONE_MONITOR has id standalone-monitor, standaloneInvocable false, and COMMIT_PUSH/MONITOR slots with canonical monitor_fix -> commit_push -> monitor traversal. StandaloneMonitorStrategy and StandaloneMonitorPublicationStrategy have explicit declared roles and registry-validated identities, policies, steps and accepted bindings. Existing MONITOR/PR/STANDALONE bindings and both legacy strategy files remain unchanged.
2. A prepared standalone execution entry acquires resources before status publisher construction, current execution branch/base capture, facts, records, repair prompts or plan initialization. It carries immutable optional target/execution facts and uses the owned path everywhere in execution. runForGoal bypasses standalone normalization/preparation/status, and legacy paths retain their checkout and branch guard.
3. The first standalone publication visit settles an explicit no-op with no staging, commit, publication fetch or push, no fabricated commit and no pushed=true. Subsequent visits publish only an invocation-owned completed and not-yet-published repair through its accepted standalone operation. No generic local-branch push helper or second loop implements this path.
4. Identity-based standalone observation and repair preserve merged/pending/failure/conflict/no-check timeout semantics and at most three repair attempts. Invocation-local accepted evidence supplies failing logs, failed commands/assertions, actual base and target details to repair. Required local checks, repository fixes and unresolved-cause blocks are explicit in the repair directive; unchanged/local-green-only results cannot authorize publication.
5. Repair launch, staging/commit and publication guard exact identity/state/head/base against pinned/last-acknowledged values. External drift blocks rather than resets, retargets or overwrites. The adapter pushes normally to the explicit actual head endpoint/ref using advertisement expected-head validation and server old-object comparison, never force flags or a temporary remote branch.
6. Unwritable heads, missing refs, failed fetch/check/repair/push, uncertain acknowledgement and cancellation preserve incomplete work with exact target/path diagnostics. Completed publication receipts identify the acknowledged remote commit; failed/unresolved repairs cannot be marked published. Shutdown/teardown routes through the sole acquired lifecycle owner.
7. T3 and T6 execution/publication/preservation tests exist with controlled Git/fake PR services, including initial no-op, exact fork destination, accepted-capability refusal, publication-window drift, three-attempt cap, evidence/check confinement and canonical/Opus goal/PR selection preservation.

Require ancestry/normal fast-forward behavior and no force, plus sign or force-with-lease. Git's receive-pack old-object comparison then protects changes after advertisement. This enforces expected-head rejection without treating a separate API lookup as compare-and-swap.
11. Preserve any applicable original pre-push hook using the same captured input/arguments and honor its refusal. Resolve effective hook configuration before the command; unsupported preservation or guard transport fails closed with an obstacle. Generated guard logic uses validated argv/private data, never interpolated user shell text. Treat permission/fork denial, transport failure and non-fast-forward rejection as typed obstacles. Publication acknowledgement updates invocation-local last-published head only after success; on ambiguous transport result reconcile exact remote ref against attempted SHA, otherwise retain uncertain work. No GitHub/Git distributed transaction is claimed: metadata checks are preconditions and subsequent observation detects merge/close races.
12. On any exit, cancel/drain owned child repair work before subtask 1 cleanup. Failed push retains its local commit. Dirty/untracked/unknown publication state retains exact worktree/refs and reason. Bound structured/shutdown cleanup, preserve the primary failure and record independent teardown errors. Abrupt kill leaves ownership evidence for explicit stale recovery. Public mapping and final user-facing recovery/status behavior are completed by subtask 3, not by bypassing registration here.
