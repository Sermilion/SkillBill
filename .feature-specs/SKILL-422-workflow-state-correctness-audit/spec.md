# SKILL-422 Workflow state correctness audit

## Purpose

Prepare an implementation-ready audit and repair bundle for Skill Bill workflow state. Historical completed work appeared running, blocked or idle. Recent repairs addressed phantom monitors, legacy completion, process ownership, finite monitor leases and reinstall preservation of SQLite recovery files. These repairs and SKILL-414, SKILL-417 and SKILL-418 remain requirements to verify against production paths. Archived specs and the operator's baseline reset do not prove correctness. The reinstall WAL incident and recovered history require evidence preservation, not reconstructed success.

This invocation is planning only. The bundle authorizes no implementation launch, production mutation, process termination, install, commit, push or publication. The pending subtasks describe work for a separately authorized later runtime. Completion of this plan means that the executable specs and saved plans exist, not that the state audit has passed.

## Scope

Inventory every state-bearing schema, migration, store and artifact family, then trace each writer, transition trigger, transaction, recovery owner and public projection. Cover goals and decomposed parents, children and subtasks, standalone planning and other phases, verify workflows, sessions, leases, controls, progress, phase settlements and outputs, ledgers, checkpoints, finalization and aggregate records. Classify lifecycle, current step, liveness, freshness, progress and labels separately. Include CLI, MCP, common status/list/board/watch/detail, IntelliJ, desktop and tray consumers. Preserve the existing companion VS Code ordering requirement if a shared projection change reaches it.

Use existing lifecycle vocabulary. Workflow status supports pending, running, completed, failed, abandoned, blocked, paused and timed_out; its generic terminal set is completed, failed and abandoned. Workflow steps support pending, running, completed, failed, blocked, skipped and paused. Decomposition supports pending, in_progress, complete, skipped, blocked and completed_no_change, with readable completed aliasing complete. Each family must establish which members it admits. Idle and unknown describe liveness or projection; pause requested is control state; interrupted is a reason or projected step; cancelled is a progress outcome; superseded is a standalone result/activity; purged is deletion. Document unsupported transitions rather than adding tokens to fill a matrix.

The three commits have distinct failure boundaries. Subtask 1 owns durable workflow/phase acceptance and process/control ownership. Subtask 2 owns parent/planning/aggregate semantics and their public consumers. Subtask 3 owns filesystem/database maintenance and final evidence reconciliation. Each produces an inspectable repair or an evidenced no-defect result. Inventory and regression definitions stay with those changes rather than becoming separate ceremony-only tasks.

## Constraints

Production databases, recovered evidence and the user's baseline are read-only. Mutation, reset, migration, fault injection, crashes, takeover, maintenance and recovery experiments use only isolated disposable databases, an explicit disposable home/environment and owned controlled processes. Never terminate an unrelated process, back up a live database by copying its .db alone, delete the live WAL/SHM/journal/backups or repeat blanket completion. Optional read-only examination of preserved original incident evidence may document loss; unavailable evidence cannot block unrelated repair or justify invented history.

Apply runtime-command-guidance, architecture-guidelines A1-A12/G1-G7/P1-P8, runtime-kotlin ARCHITECTURE Design Principles, code-principles and observability-policy as summarized in the preplan digest. Later implement confirms current owners before changing them. Keep policy in domain/application/engine, JDBC/process inspection in adapters and composition in runtime-core. Inject time and host facts. Use typed inner APIs, owning keys/enums, typed failures and observable refusals. Authored Kotlin has no line/block comments; interface/member KDoc is permitted. Do not add generic transports, forwarding abstractions, dependency bags or unrelated refactoring.

Phase authority remains explicit. Implement and audit inspect the tree and author production code, tests and evidence definitions; they do not execute builds, tests, generators or installers. Build alone owns the pack build command. Validate alone executes required suites and controlled experiments. Runtime-owned history, exact-tree review, commits, PRs and installation remain with their owners; these artifacts do not launch them. Later review/validation repair may adjust production wiring, fixtures, formatting, lint or files beyond the starting path list when necessary for these outcomes. Operator constraints and isolation remain binding.

## Validation strategy

Planning performs artifact-format, path-safety, dependency and coverage checks only. It executes no tests, compilation, builds, installers or full check suites. tests_executed is empty. Later validate owns disposable reproductions, before/after observations, persistence after reopen/restart and the execution evidence needed to mark a finding verified closed. A tree with a regression test is not an executed regression receipt.

Packaged CLI/MCP fixture prerequisites belong to the proper runtime/build owner. Scheduled verifyPlugin stays separately owned. Validate discovers current required commands and repairs failures; runtime-only validation cannot stand in for desktop or IntelliJ coverage. unit-test-value-check remains the runtime-owned gate, never an extra standalone operation launched by this plan.

Run deterministic isolated scenarios using reopenable production stores, existing shared SQLite fixtures, explicit environments, fixed/mutable injected clocks, supervisor substitutes and synchronization barriers rather than sleeps. Each subtask plan names the wrong behavior its tests catch. If an existing high-value test proves a branch, extend or reuse it instead of duplicating literals. Preserve past-bug and parity tests. Changed contracts require schema-first owner/version/key/failure-code and producer/consumer compatibility evidence. Source/skill or installer changes have their required install action only under later owner authority, in isolation for regression execution.
