# SKILL-430 subtask 2 - Single runtime copy

## Parent

`.feature-specs/SKILL-430-single-runtime-copy-for-desktop/spec.md`

Covers parent acceptance criteria 5, 6, 8, 9, 10 and 11. Criteria 5 and 9 share one criterion below because both state what the bundle contains. The `PackagedDataSmoke` part of parent criterion 11 is a test obligation, since criteria cannot name tests.

## Scope

- Switch the four `jvmMain` runtime dependencies in `composeApp` and `core/data` (`runtime-core`, `runtime-contracts`) to `compileOnly`. Test dependencies stay `implementation` so jvmTest keeps a test-provisioned runtime. The `includeBuild("../runtime-kotlin")` composite stays for compilation.
- Packaging (in `DesktopApplicationConventionPlugin`) keeps runtime modules out of `lib/app` and drops the desktop's copies of libraries the installed runtime already ships, so each shared library loads once, from the runtime. Subtask 1's version check guarantees the versions agree.
- A bootstrap entry point becomes `compose.desktop.application.mainClass`. It uses only JDK types across the loader boundary and no `skillbill.*` runtime imports. It resolves the runtime root the same way subtask 1 does (`SKILL_BILL_RUNTIME_DIR`, else `<user.home>/.skill-bill/runtime`), reads `runtime-cli/build-identity.properties`, compares it with the desktop record using subtask 1's comparison, then builds a `URLClassLoader` whose parent is the platform loader. That loader holds the desktop app jars and `<root>/runtime-cli/lib/*.jar`. The bootstrap sets the thread context loader and calls `dev.skillbill.tray.composition.MainKt.main`. A launch property names the delegated main class (default `MainKt`) so the packaged smoke can go through the bootstrap.
- On a missing runtime or a mismatch the bootstrap loads no runtime class. Decision: it shows the dedicated failure state as a small JDK-only window with the reason (including "runtime not installed"), both identities, the reinstall command and a Retry that re-reads the record and continues on a match. It reuses subtask 1's reason and message wording.
- Reflection guard. The delegated `main` call is reflective lookup by intent, whichever API it uses. Decision (preplan U2): record an operator-approved deviation in `desktop-tray/agent/decisions.md` modeled on the 2026-10-15 entry, scoped to the bootstrap source. The parent constraint is the operator approval. The `reflectiveLookup` rule keeps covering every other production source, and no baseline or allow-list grows. If the guard needs a code change to admit the bootstrap, the change names that one source and comes with the decisions entry.
- `RuntimeWorkAdapter`, the board and detail repositories, `DesktopCommitSignalObserver`/`DesktopCommitSignalSource`, `RuntimeWorkControlRepository` and `DetachedWorkRunLauncher` keep their code; they now run on the installed runtime's classes. `DatabaseSession` still calls `upgradeExistingStore` (decision 2026-10-14), which now executes the installed runtime's migrations.
- Docs: a new `desktop-tray/agent/decisions.md` entry ("Desktop loads the installed runtime; build identity gates startup") that cites "Read work through the runtime store" and notes how it changes "Keep the desktop build independent". `desktop-tray/ARCHITECTURE.md` passages about composite bundling, packaging, CI, Room/runtime migrations and source builds describe the bootstrap and identity check instead. Final `install.sh` usage text and the README install section describe the matched pair.
- CI: `desktop-tray-ci.yml` adds `runtime-kotlin/**` to its paths, provisions a runtime (`:runtime-cli:installDist` with its identity record) before `packagedDataSmoke`, and fails if the packaged image has runtime module jars. `release.yml` builds the runtime before packaging the desktop and fails if the desktop archive contains a runtime module jar.

## Acceptance Criteria

1. The desktop `jvmMain` source sets depend on runtime modules only through `compileOnly`, and the packaging configuration produces a `lib/app/` with no `runtime-*` jar or other Skill Bill runtime module jar, so no code in the desktop bundle applies a migration or carries a migration list. The installed runtime is the only migration and schema-compatibility authority.
2. The packaged desktop's main class is a bootstrap that resolves the runtime install root (`SKILL_BILL_RUNTIME_DIR`, else `~/.skill-bill/runtime`, jars from `runtime-cli/lib`), runs the subtask 1 identity check, builds the application class loader from the desktop jars and the installed runtime jars, and invokes `dev.skillbill.tray.composition.MainKt`. A missing runtime install shows the dedicated failure state with a "runtime not installed" reason, with no `ClassNotFoundException` and no runtime class loaded.
3. `RuntimeWorkAdapter`, the board and detail repositories, the sidecar change signal, and every work control (resume, pause, cancel, choose agent) run unchanged against the installed runtime's classes, and `DetachedWorkRunLauncher` still launches the installed `skill-bill` for runs.
4. `desktop-tray/agent/decisions.md` records the decision that the desktop loads the installed runtime and build identity gates startup, plus the bootstrap reflection deviation if the guard needs one. `desktop-tray/ARCHITECTURE.md` describes the bootstrap and identity check in place of composite-build bundling. `install.sh` usage and the README install section describe the matched runtime and desktop pair.
5. `desktop-tray-ci.yml` and `release.yml` provision the runtime before packaging or smoke-testing the desktop, and each fails when the packaged desktop image or release archive contains a Skill Bill runtime module jar, so the release desktop asset ships without runtime jars.

## Non-Goals

- Running the installed CLI for reads, PATH discovery for reads, or parsing command output in the desktop (SKILL-423 design stays).
- Merging the CLI or MCP launchers into the desktop, or making the CLI depend on a desktop install.
- Changing `DetachedWorkRunLauncher`, adding migrations, schema downgrade, or cleaning already-migrated databases.
- Editing files inside a packaged macOS bundle at install time (signing). The identity stays a packaged resource.

## Dependency Notes

- Assumptions for implement to confirm: Compose/Skiko native loading, `Dispatchers.Main` service lookup, `java.util.prefs` and kotlin-inject generated code work from the bootstrap loader (preplan R2); whether the bootstrap needs its own small module or fits in `composeApp` (a new module needs `include(...)` and allowed-edge entries); whether Swing/AWT use in the bootstrap trips any desktop source rule; the README install section heading, located by implement.
- Architecture test inputs in `composeApp` jvmTest keep reading runtime sources through the composite (R9).

## Test Obligations

- `PackagedDataSmoke` and `scripts/packaged-data-smoke.py` provision a runtime root (the composite's `:runtime-cli:installDist` output with a matching record, via `SKILL_BILL_RUNTIME_DIR` or the temp home) and launch through the bootstrap using the delegated-main property instead of rewriting `app.mainclass`. Catches a bootstrap that cannot assemble a working classpath from installed jars.
- Bootstrap "runtime not installed": an empty runtime root yields the not-installed reason without loading a runtime class. Catches a `ClassNotFoundException` regression.
- Other desktop jvmTests that build `RuntimeComponent` in-process keep their test-scope runtime dependencies; no new tests for them.

## Implementation Details

Settled decisions from the preplan digest. Implement confirms the items marked "Assumption".

- The bootstrap lives in `composeApp` jvmMain as package `dev.skillbill.tray.bootstrap` (file `DesktopBootstrap.kt` plus `RuntimeMissingWindow.kt`). It is not a new Gradle module, so no `include(...)` change and no allowed-edge or `RuntimeModuleCatalog` change. Assumption: `composeApp` already depends on `core:data`, where subtask 1 put the JDK-only record reader and comparison. If that comparison class pulls in anything beyond JDK and kotlin-stdlib, implement moves the pure comparison into a JDK-only file the bootstrap can call. Implement keeps one copy of the logic and does not fork it.
- Launcher classpath vs application loader. The Compose launcher still puts every `lib/app` jar on the system classpath. The bootstrap uses only kotlin-stdlib, the JDK and the subtask 1 comparison from there. The application `URLClassLoader` has the platform loader as its parent and holds every `lib/app/*.jar` (bootstrap jar included, since only strings cross the loader boundary) plus `<root>/runtime-cli/lib/*.jar`. A `lib/app` jar whose artifact name (the file name minus its version suffix) also appears in the runtime lib is skipped, so each shared library loads once, from the runtime, inside the application loader.
- Packaging keeps the desktop's kotlin-stdlib (and `annotations`, if stdlib needs it) in `lib/app`, because the Kotlin bootstrap needs it on the launcher classpath. The application loader still skips it in favor of the runtime's copy. This narrows the Scope line "drops the desktop's copies" for stdlib only. Every other shared third-party jar is dropped at packaging. Assumption: subtask 1's version check exposes the shared module set (group:module of the runtime's `runtime-cli` runtime classpath) in a form the packaging exclusion can reuse. If it does not, implement derives the set from the same detached configuration and does not keep a second hand-written list.
- Delegated main class property: `-Dskillbill.desktop.mainClass=<fqcn>`, defaulting to `dev.skillbill.tray.composition.MainKt`. Runtime root resolution is the one subtask 1 function: `SKILL_BILL_RUNTIME_DIR`, else `<user.home>/.skill-bill/runtime`. The bootstrap passes `System.getenv()` and `System.getProperty("user.home")` into it, because it runs before DI and `HostEnvironment`.
- Failure window: a Swing `JFrame`/`JOptionPane`-style window built only from JDK types. It shows the subtask 1 reason text (mismatch, missing/unreadable record, "runtime not installed"), both identities, the reinstall command, and Retry and Quit buttons. Retry re-runs resolution and the comparison. On a match the window closes and the bootstrap continues to the delegate. Assumption: no desktop source rule bans `javax.swing`/`java.awt` in `composeApp` jvmMain. If one does, the window uses `java.awt` only or the bootstrap gets a one-file exemption, recorded in the same decisions entry as the reflection deviation.
- "Runtime not installed" means `<root>/runtime-cli/lib` is missing or has no jar. A missing or unreadable `build-identity.properties` next to an existing lib gets the subtask 1 "missing/unreadable" reason.
