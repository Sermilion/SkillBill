# SKILL-427 - concurrent standalone PR monitoring in owned worktrees

decomposed

## Intended Outcome

Two standalone monitor invocations can watch and repair different PRs of the same repository from one dirty checkout. Each invocation resolves its exact target and operates in an invocation-owned Git worktree. The caller keeps its branch, HEAD, index, tracked edits, and untracked files. Goal monitoring and monitoring inside phase pr keep their existing behavior.

## Acceptance Criteria

1. Standalone monitor resolves an explicit URL to that exact repository/PR and actual head/base, or resolves an exact issue key uniquely without a tracker. Invalid, missing, ambiguous, mismatched, or incomplete explicit targets produce actionable refusals before checkout or publication, with no fallback to the caller's PR. Omitted intake resolves the caller branch's open PR or completes with a useful no-open-PR report. An explicitly merged target completes identified; an explicitly closed-unmerged target blocks identified.
2. Every executable standalone monitor uses a uniquely owned worktree at the published target head before status registration, execution facts, branch records, repair prompts, or execution planning capture its checkout. Repair files, agents, checks, Git changes, commits, and pushes are confined there. A target head already checked out elsewhere remains monitorable without moving that branch or changing the caller's HEAD, index, or pending files.
3. Standalone monitoring watches published CI first and publishes only a completed repair from its own invocation to the resolved head repository/ref, including writable forks. Publication uses a normal fast-forward update guarded against unexpected advertised head changes. It never force-pushes or creates a remote branch from the temporary local name. Unwritable heads and publication failures identify the obstacle and preserve unpublished repairs.
4. The standalone slot implementation preserves CI semantics: merged completion, pending waits, failing-plus-pending and conflicts routed to repair, evidence-led investigation and required local checks, unresolved causes blocked, the one-hour no-checks obstacle, and a maximum of three repair attempts. Polling and repairs address the PR by identity rather than the temporary branch.
5. Different PRs progress independently across the repository's linked worktrees. Atomic admission refuses a second live monitor of the same PR and reports its owner and target. Explicit fenced stale recovery never terminates another live process or allows an old owner to release its successor.
6. Status, events, history grouping, cancellation, replay, and final reports distinguish the exact PR, actual head branch/repository, invocation, and execution worktree while retaining the original repository identity. Different PRs cannot supersede or cancel each other even when they share an issue key or branch name. Legacy target-less status retains its interpretation.
7. Each acquired invocation owns cleanup through setup, execution, failure, and cancellation. Cleanup removes only verified owned clean worktrees and safe temporary refs. Uncommitted, untracked, unpushed, or uncertain repair state remains at its exact reported path. Setup, fetch, ownership, publication, and cleanup failures have durable diagnostics; no path silently returns to the caller checkout.
8. Target/head/base drift blocks mutation rather than silently retargeting or overwriting concurrent work. Repair launch and publication revalidate pinned identity and expected published SHA; the transport also enforces the expected advertised old SHA and server update comparison.
9. MonitorStrategy.kt and MonitorOpus55Strategy.kt remain unchanged. Their identities, policies, directives, steps, retry limits, repair behavior, and existing goal/PR/STANDALONE bindings remain unchanged. Goal monitoring still enforces its workflow branch with no standalone preparation or standalone status execution; phase pr still monitors and publishes in its workflow checkout.
10. Public monitor documentation describes exact targeting, isolated execution, repair-only publication, duplicate/stale handling, terminal/no-PR outcomes, retention/recovery, and the unchanged goal/phase-pr boundary. The public phase list remains review, validation, plan, pr, monitor, with no added listed skill or internal phase exposure.

## Design decisions

### Separate route and accepted execution

The existing SkeletonDefinition.MONITOR is shared by PhaseRunEntry.run and DefaultGoalRunnerCiMonitor through runForGoal. Rebinding it would change goal monitoring. Add internal STANDALONE_MONITOR with id standalone-monitor and standaloneInvocable false, retaining COMMIT_PUSH and MONITOR slots. Normalize only the public standalone phase monitor entry to it. Keep runForGoal, PR, MONITOR, STANDALONE, and their existing bindings intact. Record public restart arguments as phase monitor and retain public phase_id monitor.

Register StandaloneMonitorStrategy in the existing MONITOR slot and a dedicated StandaloneMonitorPublicationStrategy in COMMIT_PUSH. Reuse canonical monitor_fix -> commit_push -> monitor transitions and the three-attempt loop. The first publication visit settles an explicit no-op with no commit and no pushed=true. Later visits publish a completed, unpublished repair owned by this invocation. New declared observation/publication binding kinds select named accepted operations before generic COMMIT_PUSH dispatch. Each operation verifies accepted request identity, owner strategy, step, policy, and lifetime. No second loop, host access, or skeleton-name branch inside runStep is permitted.

Standalone monitor briefs, failing-check evidence, expected heads, completed-repair identity, and publication receipts live in invocation-local records. Do not use or modify the shared legacy MonitorFixBrief map keyed by issue key. Request facts contain typed immutable values only, with null standalone context for legacy callers.

### Preparation order and target policy

Allocate invocation identity; resolve the selector and target read-only; canonicalize repository/common-Git-directory identity; atomically admit the PR owner; immediately establish one cleanup owner; fetch the exact published head into invocation-specific refs; create a unique local branch/worktree at that SHA; verify head/base mapping; replace execution repoRoot and resolved branch/base facts; then construct status registration, facts, records, repair launch context, strategy selection, and the ordinary execution plan/run loop. Setup failure uses the same owner to unwind partial resources. Terminal/no-target results need no execution worktree and must not fabricate one.

Before preparation, read-only target resolution may inspect caller repository metadata. Thereafter execution observations and effects receive the owned path. Shared ownership files and temporary Git refs necessarily live under the common Git directory, but never mutate the caller's index or branch refs. No stash, reset, checkout, staging, configuration rewrite, or commit in the caller.

URL selection requires a recognized GitHub host, exact repository and PR number, caller base-repository match, and complete head/base data. Fork heads are allowed. Issue keys match complete key tokens in PR title, body, or head ref using paginated repository-wide results. Exactly one open match is selected; multiple open matches block with candidate URLs. If no open match exists, a single terminal match follows the merged/closed policy; multiple terminal matches block; no match blocks. Omitted intake uses the caller's branch and head-repository identity to resolve an open PR uniquely; no open match completes, ambiguity blocks. Never consult a tracker or choose a first result/page arbitrarily.

The target includes canonical host/base-repository identity and PR number/URL, head repository and fetch/push endpoints, head ref/SHA, base repository/ref/SHA, state, and permission evidence. Unsupported hosts, malformed input, missing/deleted head, unavailable permissions, and incomplete data refuse before checkout. A merged explicit target completes without repair; closed-unmerged blocks. During execution, merge completes and closure blocks before further mutation.

### Ownership and recovery

Use stable canonical Git common-directory identity for cross-worktree admission, plus canonical host/base-repository/PR identity as the target key. Preserve the existing repository-identity owner for status grouping using the primary repository root. Do not globally redefine repository identity.

Under <common-git-dir>/skill-bill/standalone-monitor/<target-key-hash>/ keep a stable lock file and versioned owner.json metadata. Acquire a cross-process file lock and hold it for the resource lifetime. Same-JVM overlapping locks also return duplicate refusal. Atomically replace metadata under that lock; never unlink/recreate the lock file. Metadata records target, invocation, unique owner token, monotonically increasing generation, host/process-start identity, caller/primary roots, execution path, owned branch/fetch refs, pinned and last-published heads, lifecycle state, timestamps, and retention/failure reason. Token and generation fence every mutation and release.

Select the monitor-only option --recover-stale-owner <owner-token>. It requires an explicit target URL or issue key, an acquirable lock, an exact stored token, and positive evidence that that exact former host/process-start identity is gone. Expiry or an unknown/remote host is insufficient. It never signals a process. Retained repair work blocks automatic reacquisition even with this option and reports the path for operator recovery. Safe clean stale resources may be cleaned under the new fenced generation after ownership verification. Recovery never silently adopts unfinished repairs or overrides an active owner.

Introduce orchestration/contracts/standalone-monitor-ownership-schema.yaml at contract_version 1.0, its owning Kotlin version constant and key object, parity tests, and typed runtime failure codes. Strictly reject malformed, unknown-version, or incoherent records. Quarantine/regenerate only within the repository's established runtime contract policy and only when no live lock owner exists; never treat a parse error as permission to delete resources. Corrupt/unknown metadata otherwise blocks with a diagnostic path. Keep lifecycle tombstones and monotonically increasing generation metadata so release cannot erase fencing history.

### Guarded publication

Choose an ordinary git push with an invocation-scoped pre-push guard, not force-with-lease. A private hooks directory under owned metadata supplies a guard for the explicit resolved remote URL and refs/heads/<actual-head>. It checks the same receive-pack advertisement consumed by Git: exactly one intended ref update, local object equal to the completed repair commit, and advertised old object equal to the expected last-observed/published head. An absent or changed ref aborts before sending an update. A non-force explicit refspec and local ancestry check enforce fast-forward publication. Git's server-side old-object comparison rejects changes after advertisement. Fail closed if the installed transport cannot provide this guard. Test both advertisement-time and server-update-time races.

Do not mutate shared core.hooksPath or remote configuration. Pass the hooks path only on this command. Preserve an existing applicable pre-push hook by forwarding the captured input/arguments and honoring refusal; failure to preserve an applicable hook blocks rather than bypasses it. Generate fixed hook logic with validated arguments and invocation-local guard data, not interpolated operator shell text. Do not claim a GitHub-metadata transaction: API identity/state/base rechecks are preconditions, while the Git update protects the head ref. A merge/close race cannot be made atomic with that Git update and must be reported from the next identity observation.

Before repair launch, before staging/commit, and immediately before publication re-read exact target identity/state/head repository/ref/SHA and base. Compare against the pinned tuple and last acknowledged push. Block any external head/base change, including base advancement during a repair. Conflicted repair merges the pinned actual base, not caller origin defaults. On push uncertainty retain work, reconcile the explicit remote ref against the attempted commit, and never mark published until acknowledged or positively reconciled. Publication failure retains the commit and path; no automatic reset, retarget, or force push.

### Status, storage, and cancellation

Add typed optional monitor metadata to status DTOs and additive nullable SQLite columns. Use exact PR identity first for status/history grouping. Store actual head branch as branchCorrelation, caller root separately from execution root, and original repository identity for grouping. Target-bearing monitors bypass legacy same-branch supersession, and legacy supersession queries exclude them. Original-repository status reads include target-bearing rows independently of the caller's current branch; target-less rows retain existing branch scoping.

Use existing typed status summary/detail fields for PR URL, real branch, invocation, worktree, and retention/recovery reason. No new public IDE wire fields or ide-status schema bump are planned. Append the next available database migration after the implementation checkout's latest migration, which was 57 at discovery. Preserve sequence, revision, lease, launch arguments, agent environment, and legacy records; reject partial/corrupt new metadata tuples.

Cancellation remains repository/execution/revision/owner-specific. Replay uses the recorded exact PR URL and public phase monitor arguments, skips caller checkout of the target branch, and re-enters preparation. Retained unfinished work produces an explicit recovery obstacle/path, not fresh automatic work. Stop and drain owned child activity before cleanup. Use structured cancellation plus a bounded shutdown fallback for process termination; abrupt kill leaves diagnosable stale ownership. Never claim finally handles SIGKILL.
