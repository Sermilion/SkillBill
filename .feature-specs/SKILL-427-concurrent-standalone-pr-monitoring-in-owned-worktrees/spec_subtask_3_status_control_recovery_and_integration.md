## Acceptance Criteria

1. Target-bearing status DTOs and additive nullable SQLite storage preserve canonical PR identity/URL, actual head repository/branch, caller root, execution worktree, invocation and cleanup/retention detail. New tuples parse strictly, legacy null tuples keep their interpretation, and the next appended migration preserves old sequence/revision/lease/launch/environment data.
2. Target-bearing monitor registration never invokes branch supersession; legacy supersession excludes target-bearing rows. Status reads discover target executions through original repository identity regardless of caller branch. SQL and in-memory history grouping prefer PR identity over issue/workflow/branch, so distinct PRs with matching issue/head names remain independent. Admission stays in the fenced resource gate, not best-effort status.
3. Status/events/final reports show exact target URL, actual branch/repository, invocation, execution worktree and cleanup/retention reason through existing summary/detail transport fields. Target-less paths keep legacy branch-scoped behavior. Early terminal/refusal outcomes identify their selector/target and have no fabricated worktree.
4. Cancellation targets the exact invocation/execution/revision/owner and cannot stop another PR. Restart replays the recorded exact URL through standalone preparation without checking out the target in the original checkout. Retained unfinished work blocks automatic fresh replay with its exact recovery path/reason.
5. Public phase monitor alone selects internal STANDALONE_MONITOR after read-only target resolution and owned preparation, before registration/facts/branch capture. Public names and stored phase monitor arguments stay stable. --recover-stale-owner <owner-token> is monitor-only, requires explicit target and follows the fenced dead-owner policy; malformed/inapplicable options refuse actionably.
6. The authored Phase Monitor and runtime command guidance describe exact intake, terminal/no-PR behavior, worktree isolation, watch-first/repair-only publication, stale/duplicate admission, retention/recovery, cancellation limits and unchanged goal/phase-pr behavior. Generated SKILL.md/pointers/provider artifacts are absent from the authored change.
7. T4 status/migration/control, T5 controlled-Git concurrent integration and T6 route-preservation tests exist. They prove two target PRs from one dirty checkout keep separate execution/check/prompt/publication/status/cancellation state, including checked-out head and issue/head-name collisions, and preserve the caller HEAD/index/files and existing canonical/Opus goal/phase-pr behavior.
8. Setup/runtime/cancellation/cleanup failures retain primary and secondary evidence in ownership diagnostics and available status/final reporting. The cleanup owner starts at acquisition, drains owned children and never removes dirty/unpublished/uncertain or operator-owned work. An abrupt process kill is represented as stale recovery with retained evidence rather than guaranteed cleanup.
