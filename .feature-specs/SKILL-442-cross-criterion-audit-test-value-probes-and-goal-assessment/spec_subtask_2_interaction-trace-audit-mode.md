# SKILL-442 subtask 2 - interaction trace audit mode

## Scope

Parent criterion AC-002, except the handling of `unknown` verdicts (subtask 3) and telemetry (subtask 8). Parent AC-001's "catalog next to the criterion catalog, keyed by spec digest" is also delivered here, because the trace is its first reader. This subtask also lands the contract fields AC-003's re-check needs, so the repair-state contract moves from `0.1` to `0.2` once instead of twice. Subtask 3 writes and reads those fields.

Shared decisions restated from the parent: `interaction_trace` is a runtime-scoped invocation of the existing `audit` step, with no new phase id. Verdicts travel as parsed prose lines in the existing `feature_task_phase_complete` value. A malformed output gets one re-ask inside the existing attempt budget, then degrades to `unknown` with a `RuntimeDiagnosticsBestEffortWarning`. Reopened criteria use the existing `MAX_UNSUCCESSFUL_REPAIR_OUTCOMES` (3) budget and its existing exhaustion behavior. No new block reason, budget, or MCP argument.

Trace line grammar, one line per traced item, at the end of the audit prose: `Interaction <ref>: holds trace <citations>`, `Interaction <ref>: broken owner <AC-NNN> trace <citations>`, or `Interaction <ref>: unknown trace <citations or reason>`. `<ref>` is a scenario ref `IS-NNN` or a same-file pair ref `AC-NNN+AC-NNN` (lower ref first). `<citations>` is a comma-separated list of `path:line` or `path:start-end` steps from the entry point to the outcome.

## Interaction Scenarios

1. IS-001. Criteria: AC-002, AC-004.
   Entry point: the `audit` step of a goal subtask whose catalog has IS-001 crossing AC-001 and AC-002.
   Preconditions: both criteria are accepted; each holds alone; the IS-001 flow is broken in production.
   Steps: the runtime launches the trace; the auditor returns `Interaction IS-001: broken owner AC-002 trace ...`.
   Outcome: AC-002 is `source_unresolved` with the trace as its gap, sits in `regressed_refs`, and the next step is `audit_plan_fix`. AC-001 stays accepted.
2. IS-002. Criteria: AC-002, AC-004.
   Entry point: the targeted audit that follows AC-002's repair.
   Preconditions: AC-002 was reopened by IS-001 and has one unsuccessful outcome already recorded.
   Steps: the repair lands; the targeted audit accepts AC-002.
   Outcome: the state is `interaction_trace_required` with only IS-001 pending; a `holds` re-trace moves IS-001 to `repaired_scenario_refs`; review starts after that.
3. IS-003. Criteria: AC-002, AC-004.
   Entry point: the trace settlement.
   Preconditions: the auditor's output has no `Interaction` lines, twice.
   Steps: the runtime re-asks once, then records the second output.
   Outcome: one best-effort warning, every pending ref in `unknown_scenario_refs`, no criterion reopened, and audit moves forward to review.
4. IS-004. Criteria: AC-001, AC-002.
   Entry point: admission of an audit result.
   Preconditions: a `current_criterion_targeted` result reports `regressed_refs: [AC-001]`.
   Steps: the recorder submits it to admission.
   Outcome: admission rejects it as before; only an `interaction_trace` result may carry regressed refs.

### Evidence and decisions

- `FeatureTaskRuntimeRunEntry.inspectRepairState` constructs the binding from the admitted criteria and spec digest, then restores repair state. `AcceptanceCriterionRepairPersistence.inspectExisting` constructs another binding. Both must receive the same catalog and digest. An empty catalog is valid only for a valid spec with no scenarios. Parser issues must retain subtask 1's typed failure behavior, rather than silently replacing malformed input with an empty catalog.
- `AcceptanceCriterionRepairAuditAdmission.matches` currently admits evidence only for `Discover` and targeted `Outcome` mutations. `noGraphChanges` rejects both regressed refs and edge changes. Trace settlement needs its own mutation and evidence branch, while existing branches retain their restrictions.
- `AcceptanceCriterionRepairPhaseRecorder.complete` returns immediately for stage `ACCEPTED`. `completeExisting` derives output identity, prose, tree digest, and checkpoint identity, while `auditEvidence` only reads a structured output agents do not produce. The runtime must construct trace evidence from parsed prose and these bound identities, then use ordinary admission and the existing owning write transaction.
- `AcceptanceCriterionRepairCoherence.reopeningIsCoherent` currently requires an unsatisfied, criterion-specific `AcceptanceCriterionProseAudit` matching each source transition. A trace cannot append an unbacked reopening transition. Record a matching prose audit for each broken owner, with distinct owner-bound identity derived from the producing output, and preserve the existing history invariants.
- `AcceptanceAuditRound.completionRejection` returns a rejection through `PhaseOutputGate.stepCompletionRejection`. The gate calls its existing rejection handler. Rejected payload diagnostics are best-effort, so their presence cannot be authoritative retry accounting. Use a required repair-state mutation to remember the first malformed completion before returning the rejection. Reuse the existing persisted `pendingClarificationQuestion` as a bounded, runtime-owned trace rejection marker containing the failure code and a scope fingerprint. It is cleared by successful or degraded trace settlement. Trace prompt composition handles this marker separately from ordinary audit clarification.
- `AcceptanceCriterionRepairPersistence.inspectExisting` validates serial artifacts before checking for missing state. `FeatureTaskRuntimeWorkflowPersistence.validateSerialArtifacts` validates both repair-state and audit-result families on reads and writes. `AcceptanceCriterionRepairLegacyAdoption.historyIsPristine` excludes repaired or in-flight histories. Therefore treating `0.1` as absent and invoking historical adoption would strand workflows or erase attributed outcomes. Plan explicit version recovery at the owning startup boundary before current-version validation, preserving prior facts and outcomes. This is new local recovery work, not a claim that adoption already handles version mismatch.
- `FeatureTaskRuntimePhaseEvidenceRecorder` owns quarantine metadata and rejected-output diagnostics. Reuse these owners for superseded-version evidence and extend their transaction-level operation where needed. A best-effort diagnostic is not a substitute for preserving original durable records during recovery.
- There is no audit-specific path classifier. `UnitTestPathClassifier.isUnitTest` in `runtime-engine/.../operation/unittestvalue/` is the existing production classifier. Pass its predicate into the pure domain evidence helper. Do not introduce a domain dependency on engine or copy its patterns.
- `AcceptanceAuditPromptSections.sections` currently chooses ordinary or no-change scope, and its value text says no fixed format is required after discovery. Trace mode must override both task and value instructions so they consistently require the supplied trace grammar. A retained no-change claim must not override explicit trace scope or demand a no-change verdict.

The trace remains the existing read-only `audit` step. No new phase, MCP argument, blocking policy, or repair allowance is introduced. State mode stays within its existing enum; use a separate audit-result mode token owner for `interaction_trace`, rather than adding a state mode that the state schema does not accept. The trace-required stage uses accepted state mode, empty ordinary queues, and no live reservation. Reopening changes it to targeted mode and the existing repair stages.

Same-file pairs are trace targets with ordered refs `AC-NNN+AC-NNN`. Their allowed owners are the two pair members. They carry the shared production paths and both criteria's evidence so the auditor can inspect the actual callers and their combined outcome. A pair need not invent a catalog scenario or an entry point absent from the evidence. Evidence path extraction follows criterion-naming lines, falling back to the whole evidence when none name it. Shared aggregate prose can over-approximate pairs; do not claim finer attribution than the stored evidence supplies.
