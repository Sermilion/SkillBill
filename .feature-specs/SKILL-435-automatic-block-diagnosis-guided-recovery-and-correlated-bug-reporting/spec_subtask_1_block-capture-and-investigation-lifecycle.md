# SKILL-435 subtask 1: block capture and durable investigation lifecycle

## Scope

Finish the incident capture that the branch started in commits 35469cdb3 and 64bb44568, and give every incident a durable, bounded investigation lifecycle. After this subtask every actual goal block and standalone phase block creates or links exactly one incident, the original failure is never lost because incident capture failed, and a worker claims, runs and settles each new incident even when the originating process exits.

This subtask covers intake paragraphs 1 and 4 and the restart, store-preservation and primary-failure parts of parent criteria AC-001 and AC-005. Investigation content (evidence, structured diagnosis, agent pass) belongs to subtask 2. The worker in this subtask calls an investigator seam whose default settles `PARTIAL` with no structured content; subtask 2 replaces that default.

Extend the existing branch code. Do not rewrite `BlockIncidentOccurrence`, `BlockIncidentTransitions`, `SqliteBlockIncidentRepository` or migrations 66 through 75. Keep `block-incident-schema.yaml` at contract version `0.2`; this subtask adds no serialized contract fields.

## Acceptance Criteria

1. Goal-level blocks create or link a durable incident at the single goal block writer.
   `WorkflowGoalRunnerBlockWrites.markBlocked(write: GoalRunnerBlockWrite)` in `runtime-engine/src/main/kotlin/skillbill/engine/goalrunner/persist/` observes the block through `BlockIncidentService` with origin `ACCEPTED_GOAL_BLOCK` after the `WorkflowStatus.BLOCKED` write commits, for both callers: `WorkflowGoalRunnerBlockBridge.markBlocked` and `WorkflowGoalRunnerOutcomeReconcile`. Individual stop sites in `GoalRunnerGoalLoop`, `GoalRunnerSelectedSubtaskLoop`, `GoalRunnerRunPreparation`, `GoalRunnerFinalization`, `GoalRunnerSubtaskLaunchPrepare` and `GoalRunnerWorkerRequestHandling` are not hooked one by one.
   Stop reasons `BLOCKED`, `POLICY_BLOCKED` and `DEPENDENCIES_BLOCKED` all observe, because each persists `WorkflowStatus.BLOCKED`. Paused, waiting, completed, skipped and warning outcomes never reach `markBlocked` and never observe.
   The goal alias uses `BlockIncidentAliasKind.PHASE_TRANSITION` with value `<goal workflow id>:goal:<block step id>:g=<accepted generation or unavailable>:a=<accepted attempt or unavailable>:c=<causal child incident token or none>`. Generation and attempt are separate identity components, never alternatives. The causal child token comes from the accepted child block reference; `none` means this accepted block has no child cause. Use the literal `unavailable` only when the accepted historical fact cannot be recovered, never a made-up numeric default. Persist the accepted identity and carry that same reference through replay, terminal outcome reads and stale displacement after current workflow progress changes. A new accepted attempt, generation or child cause must not reuse another block's alias. Existing incident tokens and aliases remain valid immutable history; add a nonconflicting canonical alias when normalizing a proven historical identity, without rebinding an alias already owned by another incident. `PHASE_ID`, `PHASE_RUN_ID` and `ATTEMPT` are recorded present or `NOT_APPLICABLE` as the existing validator requires.
   When the block reason propagates from a child subtask workflow that already has an incident, the parent observation links a `CHILD_CAUSE` alias whose value is the child incident token to that same incident instead of minting a new token. Resolve the exact accepted child block reference, not the latest mutable child state or an unrelated historical incident. A child block in a higher attempt or generation is a new incident, and its parent alias includes that new causal token even if the parent's own generation and attempt have not changed.
   Re-observing a stale blocked outcome through `GoalRunnerStaleBlockedOutcomeContext` or `WorkflowGoalRunnerStaleBlockedOutcomeDisplacement` carries that outcome's accepted generation, attempt and child cause unchanged, derives the same alias and links to the existing incident. Never select a historical reference by list position or overwrite it with current progress.
   When the write carries a thrown failure or exit code that the runtime already turned into this durable block, the occurrence uses origin `ENTRY_FAILURE` with `exitBehavior` `THROWN` or `EXITED_WITH_CODE`, `throwableType` and `exitCode` filled; raw crashes that leave no `BLOCKED` state are out of scope.
   Standalone phases and the feature-task phase producers are criterion 2. Capture failure handling is criterion 3.
   Audit confirms by reading `markBlocked`, the alias derivation, and the child-cause lookup.
2. Standalone phase blocks create or link a durable incident, and every producer derives aliases from one shared function so one block in one attempt yields one incident.
   `StandalonePhaseStatusEventSink.settleBlocked` observes every `PhaseRunResult.Blocked` produced by `PhaseRunEntry` (the monitor-blocked branch, the `FeatureTaskRuntimeRunReport.Blocked` mapping and the remaining blocked returns) and by `QaStandalonePhaseRun`, including `MonitorPreparation.Blocked` from `StandaloneMonitorExecutionPreparer`. Its alias is `PHASE_TRANSITION` keyed on `<invocationId>:<stepId>`, and it records PR and monitor fields when present and marks them `UNAVAILABLE` otherwise.
   A new internal object `BlockIncidentAliases` in `runtime-engine/src/main/kotlin/skillbill/engine/diagnostics/block/` is the only alias derivation. `FeatureTaskPhaseSettlementService.block`, `FeatureTaskRuntimePhaseStateRecorder.observeAcceptedBlock`, `AcceptanceCriterionRepairPersistence.observeSerialBlock`, the standalone sink and criterion 1's goal producer all call it. The invocation component comes from the admitted execution when present and otherwise from the active worker lease, so the settlement path and the recorder path for the same attempt produce the same token. When a feature-task inner block and the standalone sink observe the same attempt, the second observation links to the first incident.
   `FeatureTaskPhaseSettlementService` takes `database: DatabaseSessionFactory` as a non-null constructor dependency, and the branch that downgraded a successful block to `ERROR "block_incident_capture_unavailable"` is deleted. Feature-task producers capture after the settlement or phase-state write commits, so the block is durable before incident capture starts.
   Fallback handling when capture fails is criterion 3.
   Audit confirms by reading `BlockIncidentAliases`, each producer's call to it, the settlement constructor, and the absence of the downgrade branch.
3. Incident capture failure never removes, replaces or rolls back the primary block, and a bounded file spool keeps the failure when the database is unwritable or unreadable.
   All producers from criteria 1 and 2 call one capture entry point, `BlockIncidentCapture.capture(observation)` in `engine/diagnostics/block`, which runs `BlockIncidentService.observeBlock` in its own transaction after the block commits. Any exception from that transaction is caught there and never propagates to the producer's result.
   On capture failure, or when `DatabaseSessionFactory.databaseExists()` is false or the database cannot be opened at entry, the capture writes one spool record through a new port `BlockIncidentSpool` in `runtime-ports/src/main/kotlin/skillbill/ports/blockincident/` with methods `append(record)`, `pending(limit)` and `remove(recordId)`. The file implementation lives in `runtime-infra` and writes one JSON file per record under the runtime state directory in `block-incident-spool/`, with at most 64 records and 16 KiB per record; when full it drops the newest record and emits a `RuntimeDiagnostics` warning.
   A spool record holds only facts the producer actually had: occurrence token, alias kind and value, workflow id, parent workflow id, phase id, invocation id, attempt, origin, reason truncated to 8192 characters, failure code, failure disposition, throwable type, exit code, observed time and the capture failure code `PERSISTENCE` or `FALLBACK_SPOOL`. It never contains database evidence.
   `BlockIncidentEntryReconciler.reconcileOnEntry()` imports pending spool records on the next writable entry by calling `createOrLink` with `evidenceAvailability` `FALLBACK_SPOOL`, then removes the file. When the spool append also fails, the capture emits a warning naming evidence availability `UNSAVED` and returns.
   The worker that investigates imported incidents is criterion 4.
   Audit confirms by reading `BlockIncidentCapture`, the spool port and file adapter, the import in the reconciler, and the composition binding in `RuntimeComponent`.
4. A durable, bounded investigation worker claims, renews and settles each eligible incident, survives process exit through claim takeover, and never triggers block observation itself.
   A new `BlockIncidentInvestigationWorker` in `engine/diagnostics/block` processes incidents in `PENDING`, and in `INVESTIGATING` with an expired claim. It claims through `BlockIncidentRepository.claim` with owner token, owner generation, host identity, process id and a lease `expiresAt` of now plus 90 seconds, renews every 30 seconds, and settles through `settle`. It runs from `BlockIncidentEntryReconciler` at the start of every entry (existing call sites in `GoalRunner.run`, `FeatureTaskRuntimeRunEntry.run` and `PhaseRunEntry.run`) and once more at the end of the entry that produced a new block, bounded by the investigation deadline.
   Observation sets the incident `deadline` to a pickup window of `observedAt` plus 24 hours (new constant `INVESTIGATION_PICKUP_WINDOW` beside `INVESTIGATION_DEADLINE`). A successful claim sets `deadline` to claim time plus the existing 5-minute `INVESTIGATION_DEADLINE`. `reconcilePending` expires a `PENDING` incident past its pickup window, or an `INVESTIGATING` incident past its run deadline, to `TIMED_OUT`. Implement confirms whether the sqlite claim already writes `deadline` and adds that write if not.
   A takeover of an expired claim increments `retryCount`; past the existing `MAX_RETRIES` of 2 the incident settles `CRASHED`. An investigator exception settles `CRASHED`; a settle that fails to persist leaves the claim to expire and records a `RuntimeDiagnostics` warning. Every terminal state (`COMPLETE`, `PARTIAL`, `EXHAUSTED`, `TIMED_OUT`, `CANCELED`, `UNAVAILABLE_AGENT`, `PERSIST_FAILED`, `CRASHED`) stays visible on the incident.
   The worker calls an engine-internal `fun interface BlockIncidentInvestigator` whose default implementation in this subtask returns `PARTIAL`; subtask 2 supplies the evidence-based investigator. No worker code path calls `BlockIncidentService.observeBlock`, `BlockIncidentCapture.capture` or any settlement or recorder producer.
   The inline FQN in `BlockIncidentService.EXPIRABLE_DIAGNOSES` is replaced by an import.
   Audit confirms by reading the worker, the reconciler wiring, the transitions and the absence of observation calls in the worker path.
5. Rollout investigates only new blocks, recovers blocks whose capture was interrupted, and preserves every existing store and row.
   A new append-only migration, numbered from the next free version (expected 76), creates table `block_incident_rollout` with a single row holding `activated_at` (the migration's apply time) and `activated_schema_version`. Migrations 66 through 75 stay byte-identical.
   The worker and reconciler skip incidents whose `observedAt` precedes `activated_at`; those rows stay readable as history, are never investigated, and later subtasks never report them. Existing `BLOCKED` workflows from before `activated_at` never receive an incident.
   A new repository method `BlockIncidentRepository.blockedWithoutIncident(since: Instant, limit: Int)` returns goal and phase workflows in `BLOCKED` status updated at or after `activated_at` that have no linked alias. The reconciler observes up to 16 of them per entry through `BlockIncidentCapture`, using their persisted blocked reason and marking facts it cannot recover as `UNAVAILABLE` in `fieldAvailability`. This closes the window where a process dies after the block commits and before capture runs. Implement confirms which workflow columns carry status and update time.
   `SqliteBlockIncidentRepository` implements the new method, and `InMemoryBlockIncidentRepository` in testFixtures mirrors it.
   Audit confirms by reading the migration, the repository method and the reconciler's marker checks.

## Decisions and assumptions

The operator approved the complete accepted-identity alias on 2026-10-22 after the scalar alias made generation 2 / attempt 1 collide with generation 2 / attempt 2. This amendment supersedes the saved repair plan's generation-first scalar rule and prohibition on a composite suffix. Replan from this amended criterion and current source. Preserve completed source repairs and existing incident tokens, original occurrences and historical aliases. Do not introduce a collision counter or rewrite immutable history to make the new alias fit.

The investigation deadline counts from claim, not from observation, so a block observed while no runtime process is alive is still investigated on the next entry within 24 hours. A host-detached subprocess is not planned; the guaranteed path is claim takeover plus next-entry pickup, and the incident shows `PENDING` until then. Subtask 5 displays that state honestly.

Post-commit capture is chosen over a savepoint because it guarantees the block is durable first. The crash window between commit and capture is closed by criterion 5's orphan reconciliation.
