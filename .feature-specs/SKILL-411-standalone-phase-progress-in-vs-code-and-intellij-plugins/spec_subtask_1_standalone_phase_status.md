# SKILL-411 subtask 1: Publish standalone phase status and display the latest execution in both IDEs

## Scope and evidence

Implement one reviewable end-to-end contract across runtime status persistence/publication/selection and both plugin consumers. Cover durable standalone plan and in-memory review, validation, PR, and monitor without changing their phase semantics. The preplan digest is the sole discovery evidence for this spec; named files/symbols are implementation anchors, not verified current facts or an exhaustive edit allowlist. Confirm assumptions during implementation and repair required defects without weakening acceptance criteria or architecture guards.

This spec is future work. The current standalone plan invocation writes only its bundle, executes no implementation or checks, and does not launch a goal. Feature size is MEDIUM with full preplan, branch-diff review, and full per-criterion audit.

## Acceptance Criteria

1. orchestration/contracts/ide-status-schema.yaml and the owning Kotlin models/keys/version/serializers define a mutually consistent bumped wire contract, mirrored by both plugin decoders and governed parity fixtures. It includes explicit workflow versus standalone_phase scope, stable execution identity, cross-source ordering domain/sequence, per-execution revision, standalone requested phase/invocation identity, and optional bounded current activity. Scope is never inferred from workflow_id; invalid scope-specific payloads and version mismatch produce typed diagnostic outcomes.
2. A dedicated standalone-phase status port, typed model, SQLite repository, migration, and UnitOfWork wiring persist canonical repository/branch identity, invocation/phase identity, state, result, lease owner/generation, timestamps, and active-duration anchors. Shared sequence allocation and status transitions are atomic and idempotent; late events or a superseded lease cannot overwrite newer/settled state. Existing workflow data has a deterministic compatible migration path that does not reinterpret a phase as WorkItem or telemetry.
3. PhaseCommand, StandalonePlanLauncher/StandalonePlanRun, PhaseRunEntry, and InMemoryPhaseRunState publish available start/progress/terminal evidence for all five supported standalone phases through a bounded publisher at the existing event/lifecycle boundary. Requested phase remains stable while current internal step changes. Completion is tied to authoritative whole-invocation settlement/result, not PhaseCompleted for an intermediate step, process exit alone, or loss of a lease.
4. IdeStatusService/Projector/SelectionPolicy merge eligible workflow and standalone candidates with a common authoritative execution sequence. Their code and boundary tests select a newer completed phase over an older active workflow and a newer workflow over an older phase, break tied/skewed timestamp ambiguity by sequence, avoid duplicate durable-plan candidates, and retain existing repository/branch/goal correlation within each execution.
5. Runtime status projection/retention/reconciliation preserve established start/updated/finish/active-duration and last-agent-activity semantics. Completed results freeze timing; blocked, failed, paused, stale, and runner_interrupted remain truthful. Terminal retention survives a new polling process, late events cannot resurrect completion, expired in-memory execution cannot become done, and read/write/reconciliation failures use typed errors and RuntimeDiagnostics under existing policy.
6. VS Code's wire/domain/cache/coordinator/presentation chain renders an explicit standalone phase label, requested phase/current step, lifecycle status, evidence-backed activity when present, normal timing, and frozen terminal elapsed values in status bar, tooltip, details, and accessible text. Only genuinely active state animates. Failure, blocked, interrupted, or stale state is never presented as done; the status bar stays within its established 48-character limit.
7. IntelliJ's wire/domain/cache/coordinator/UI state/widget/popup chain provides the same observable phase identity, state, activity, timing, and accessibility behavior while preserving mutex/StateFlow lifecycle, EDT/process isolation, and existing activeElapsed/subtaskElapsed/withElapsed semantics.
8. Both plugin caches and coordinators preserve execution scope, identity, ordering domain/sequence/revision, and timing across initial subscription, refresh/reconnection, and persisted-cache restoration. Lower-order or older-revision responses do not replace a newer observed execution; transport failure and cache fallback remain stale. Authoritative expiry/store replacement can clear or replace held state without reviving an older run, and unsupported contract data is not silently coerced to idle or done.
9. Deterministic, outcome-based tests and governed fixtures cover the concrete bugs in Test obligations below across schema/storage/CLI/runtime and both plugins. The implementation includes any needed migration and package compatibility fixtures and keeps existing parity/regression assertions; no criterion requires execution of those tests during implement or audit.

Final names follow the owning key/schema conventions without losing any semantics. Required fields apply to snapshots with an execution; an empty/idle result has no invented execution. Reuse existing redaction at the publisher, strip control characters, truncate safely, and validate at the contract boundary. Retain last_agent_activity_* solely for established liveness; a timer/lease renewal is not evidence of agent work.

Older plugin versus new runtime, or newer plugin versus older runtime, must surface the existing explicit version-mismatch/degraded diagnostic behavior, never silently interpret a new scope as workflow. Ship schema/runtime and both plugin consumers as a coordinated change, using their existing packaged runtime/version surfaces. Do not add a compatibility downgrade that hides phase runs. The digest does not establish packaging APIs; implement confirms them.

### 2. Persistent source, ordering, migration, and retention

Introduce StandalonePhaseStatusRepository and a typed status model in runtime-ports/idestatus, implemented under runtime-infra/sqlite/idestatus. Expose it through UnitOfWork and construct it in SQLiteRepositories; register an additive migration in sqlite/core/migration/area. Engine owns lifecycle/selection policy, the port owns the contract, and SQLite owns transactions and resource lifetime. Use a narrow publisher collaborator, not a general service bag in phase state.

Persist canonical repository identity, captured branch correlation, requested phase, invocation id, optional durable workflow correlation, execution id/sequence, revision, state/result summary, current phase/activity, started/updated/finished timestamps, accumulated active duration and active interval anchor, plus lease owner/generation/expiry. Reuse existing canonicalization, time source, retention and lease/liveness policies; do not guess their numeric values. A small common run-order registry gives both workflow launches and standalone launches a transactionally allocated per-repository sequence in the same database generation. A run's heartbeat, phase transition, status poll, cache refresh, and nested subtask do not allocate a new sequence. An explicitly resumed root execution receives a new execution/invocation identity and sequence while preserving its durable workflow correlation and existing accumulated timing semantics. Deduplicate repeated launch registration by execution identity.

Wire the existing workflow root launch/resume boundaries to registration as well as the standalone launch boundaries. The digest does not name workflow launch APIs: implement confirms the canonical owner and adds narrowly scoped registration there, not on every status poll. Existing roots receive a deterministic transactional backfill ordered by existing authoritative start timestamps with stable identity as the tie-breaker; sequence order then owns all new launches. Existing timestamp ambiguity cannot be reconstructed, so migration documents its deterministic historical tie-break, never fabricating evidence. Polling an existing pre-migration row is not a new run. Preserve goal-authoritative selection among nested workflow candidates before comparing distinct root executions.

Lease/revision guarded updates reject stale writers and make repeated events idempotent. Status and sequence allocation share a transaction; each status state/result/timing update is one atomic write. Where durable plan settlement shares the UnitOfWork, persist its terminal status in that settlement transaction. Otherwise durable terminal state is authoritative: status may lag and be reconciled from it but may never lead it. In-memory completion publishes only after PhaseRunResult or the authoritative exception/outcome is known; missing final publication leaves an interrupted record, not inferred success. A status-write failure cannot change the underlying phase's established outcome or repeat irreversible work on retry. Surface the status failure under the repository's typed loud-fail/degradation policy with RuntimeDiagnostics and explicit degraded status, never swallow it or manufacture done.

Retain the latest eligible terminal standalone record for the same settled IDE-status retention window as workflows; do not reset its completion/expiry age on polling. Cleanup follows selection eligibility and cannot delete the latest eligible record inside that window. Keep the per-repository high-water sequence independent of retained row deletion. No telemetry-outbox or WorkListRepository proxy is introduced. On observed lease expiry, reconcile an unfinished in-memory run to runner_interrupted paused/stale, conservatively closing active accrual at the last authoritative live anchor under existing policy. Only an authoritative failure result changes it to failed. A renewed/replaced lease needs valid ownership/generation; late events from the old process cannot clear interruption or terminal state. Durable plan reconciliation uses its authoritative state before treating a missing process as interruption.

Map labels at the publisher; no event means no detailed activity. Lease upkeep reflects process ownership separately from event activity.

Requested phase identifiers are plan, review, validation, pr, monitor. Current internal steps may differ and must remain visible as steps inside the standalone run. For example, PR/monitor internal commit_push and monitor/fix steps do not create new latest-run entries. Whole-invocation result settles status; an internal PhaseCompleted does not. Completed review with findings is a completed review whose available result summary preserves findings, not an assertion of review clearance. A legitimate monitor result with no open PR is complete with its truthful summary. Blocked phase results, exceptions, cancellation, and lost processes map according to available evidence, never via an unconditional finally -> done update. ### 4. Shared plugin behavior and ordering protocol

Both adapters continue polling work status --repo-root <canonicalRoot> --format json. Initial subscription fetches runtime status; any persisted cache is explicitly stale until corroborated. Within the same status_store_id and repository, higher run_sequence wins; equal sequence requires matching execution identity and nondecreasing status_revision. An older candidate cannot replace the held latest execution even if its lifecycle is active. A same-run terminal result cannot regress to active from a stale response. Branch/project changes invalidate incompatible held identity using existing correlation rules, rather than making a global high-water mark across projects.

Do not invent a run sequence for idle. Preserve the existing one-uncorroborated-idle tolerance. Before confirmed authoritative idle clears a held record, require its established retention expiry and a fresh successful refresh in the current coordinator generation; otherwise hold it with stale diagnostics and refresh normally. Failure, timeout, malformed/version-mismatched payload, or reconnect is not authoritative idle. Store last accepted run metadata in cache; old cache format without it may be shown only as stale and must yield to the first valid snapshot. Cache fallback must never present cached terminal data as fresh done, though details may retain its last known result and timing.

A different status_store_id is a database-generation replacement, not a lower sequence. Accept it only from a successful response to the current project's latest serialized refresh generation, invalidate prior-domain ordering/cache, and reject late old-generation responses. Cancel/discard in-flight requests on coordinator disposal, repository switch, or reconnect generation replacement according to existing process isolation. These rules prevent permanent cache lockout after a database reset and prevent an old response resurrecting an earlier workflow. They do not introduce a parallel event transport.
